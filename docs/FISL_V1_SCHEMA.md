# FISL v1 Scenario Schema

**Status:** Implementation specification  
**Spec identifier:** `fisl/v1`  
**Primary consumer:** Python scenario compiler  
**Runtime consumer:** Factorio FISL core mod (resolved semantics + run configuration)

This document turns ADRs 0001–0018 into the first implementation-grade scenario shape.

The exact Pydantic class names and JSON Schema generated by the implementation may differ, but the semantic structure and validation rules in this document are normative for v1.

---

## 1. Three representations: authoring YAML, `ResolvedScenario`, and `RunConfiguration`

Scenario authors write YAML for readability. The compiler produces a stable run-independent resolved scenario. The controller then binds one concrete execution attempt to that scenario with a separate run configuration.

```text
scenario.yaml
    |
    | parse + validate + resolve
    v
ResolvedScenario / scenario.resolved.json
    |
    | canonicalize + hash
    v
resolved_scenario_hash
    |
    | bind run_id + actual seed
    v
RunConfiguration / run-config.json
    |
    | runtime envelope / RCON transport
    v
FISL Lua runtime
```

### Authoring form

May contain human-friendly values such as:

```text
5m
30s
60/min
unbounded
```

and references such as:

```text
window.phase: measured
flow: workpiece_flow
```

### `ResolvedScenario`

Contains only explicit **run-independent experiment semantics**, including:

- integer experiment ticks;
- rational rate definitions;
- explicit phase boundaries;
- explicit window boundaries;
- normalized capacities;
- resolved cross-references/IDs;
- time/game-speed/pause policy;
- zone/system/entity-set definitions;
- port, flow, metric, objective and visibility semantics;
- observation-plan semantics;
- versioned schema/compiler semantic metadata.

It explicitly does **not** contain:

```text
run_id
actual experiment seed
wall-clock timestamps
learner/team metadata
RCON credentials/ephemeral ports
run output paths
```

The canonical `ResolvedScenario` is hashed to produce `resolved_scenario_hash` under ADR 0013.

### `RunConfiguration`

Contains the per-attempt execution binding, at minimum:

```text
run_id
resolved_scenario_hash
actual experiment_seed
protocol/config envelope version
```

It may additionally contain run-scoped references/checksums required by the controller/runtime handshake, but it is not the input to `resolved_scenario_hash`.

Changing `run_id` alone must not change the resolved scenario identity or reproducibility fingerprint. Changing the actual experiment seed does not change `resolved_scenario_hash`, but does change the reproducibility fingerprint.

Lua does **not** parse YAML or independently reinterpret authoring shorthand.

## 2. Top-level authoring shape

```yaml
spec: fisl/v1

scenario: {}
factorio: {}
experiment: {}
zones: {}
systems: {}
entity_sets: {}
ports: {}
flows: {}
metrics: {}
objectives: {}
visibility: {}
learning: {}
```

Required top-level sections for a runnable scenario are:

```text
spec
scenario
factorio
experiment
zones
systems
```

Other sections are required only when referenced/needed by the scenario.

Unknown fields SHOULD be rejected by default so typos do not become silently ignored experiment changes.

```yaml
    - service constraints

    - equipment failures
    - labor behavior
    - monetary cost

  warranted_conclusions:
    - compare physical flow and inventory consequences under the declared deterministic assumptions

  not_warranted:
    - infer that human organizations behave like deterministic Factorio machines
```

The authoring `experiment.seed` above is a default. The controller resolves the actual run seed when constructing `RunConfiguration`; it is not copied into canonical `ResolvedScenario` identity.

## 4. Scalar authoring conventions

### 4.1 Durations

Accepted forms include integer tick literals in resolved/configuration APIs and author-friendly strings:

```text
120t
30s
5m
```

Compiler conversion is exact:

```text
1s = 60 ticks
1m = 3600 ticks
```

Durations that cannot resolve exactly to an integer tick are rejected.

### 4.2 Rates

Author forms such as:

```text
60/min
180/min
1/s
```

compile to an exact rational schedule definition:

```json
{
  "quantity_numerator": 60,
  "period_ticks": 3600
}
```

The runtime uses exact integer/rational accumulation as required by ADR 0003; it does not accumulate floating-point items-per-tick drift.

### 4.3 Capacities

Author forms:

```yaml
capacity: 0
capacity: 2000
capacity: unbounded
```

resolve to an explicit tagged union such as:

```json
{"kind":"finite","quantity":2000}
```

or:

```json
{"kind":"unbounded"}
```

### 4.4 Percentages/ratios

Scientific ratios are represented internally using exact numerator/denominator data where available. Author thresholds such as `0.95` are normalized deterministically by the compiler; result formatting is presentation-only.

## 5. `scenario`

Required:

```yaml
scenario:
  id: fp-03-littles-law
  version: 1.0.0
  title: WIP and Cycle Time
```

Rules:

- `id` is stable, lowercase/kebab-case recommended;
- `version` is SemVer-compatible;
- title/description are explanatory metadata;
- source hash and resolved-scenario hash are generated, not authored.

---

## 6. `factorio`

```yaml
factorio:
  version:
    minimum: 2.0.77
    maximum_exclusive: 2.1.0
  baseline_save: baselines/fp-03.zip
  required_mods:
    fisl-core: compatible
```

Compiler/controller validates:

- baseline path exists;
- baseline hash is recorded;
- actual Factorio version satisfies constraint;
- required mods are present/compatible.

The first implementation SHOULD pin a tested Factorio stable version rather than relying only on a broad range.

---

## 7. `experiment`

### 7.1 Seed

```yaml
experiment:
  seed: 1
```

This is an authoring default / requested run input, not part of stable `ResolvedScenario` identity.

CLI may override it. The controller determines the actual execution seed and stores it in `RunConfiguration` and provenance.

The reproducibility fingerprint includes the actual seed even though `resolved_scenario_hash` does not.

### 7.2 Time policy

```yaml
experiment:
  time:
    game_speed:
      policy: fixed
      value: 1.0
    pause_policy: prohibited
```

V1 game-speed policy is `fixed`.

The canonical interactive POC profile supports:

```text
pause_policy: prohibited
```

under ADR 0018. The local server must disable incidental zero-player auto-pause, and unexpected required-learner disconnect during RUNNING aborts the interactive attempt while preserving data.

`allowed` remains a reserved future policy but SHOULD be rejected by the initial interactive POC implementation until controlled pause/resume semantics are explicitly implemented and tested.

### 7.3 Phases

```yaml
phases:
  - id: warmup
    duration: 5m
  - id: measured
    duration: 20m
```

Compiler resolves contiguous half-open intervals beginning at experiment tick zero.

Each ID is unique and each duration is positive.

## 8. `zones`

```yaml
zones:
  factory_floor:
    surface: nauvis
    area:
      left_top: [-50, -30]
      right_bottom: [50, 30]
```

V1 zones are:

- static;
- rectangular;
- surface-specific;
- half-open in geometric membership;
- tile-aligned in authoring validation.

---

## 9. `systems`

```yaml
systems:
  factory:
    primary_zone: factory_floor
    boundary_integrity:
      entity_containment: flag
```

V1 has one primary spatial zone per system.

Suggested containment policies:

```text
flag
require
```

`flag` preserves the run and emits protocol diagnostics. `require` may prevent READY/start if the baseline already violates containment and may flag/abort according to scenario policy during the run.

Exact enforcement behavior is an implementation profile; the accounting boundary remains separate from geometry.

---

## 10. `entity_sets`

```yaml
entity_sets:
  line_machines:
    zone: factory_floor
    types:
      - assembling-machine
      - furnace
    prototypes: []
    exclude_roles:
      - fisl_apparatus
    membership: dynamic
```

V1 production sets default to dynamic membership under ADR 0016.

Supported selector fields:

```text
zone
types
prototypes
include_roles
exclude_roles
```

The compiler rejects selectors with no positive scope unless a future explicit global set is allowed.

## 11. `ports`

Every port declares:

```text
system
direction
binding
material
```

### 11.1 Binding

Initial v1 binding form SHOULD use explicit baseline location + expected prototype:

```yaml
binding:
  surface: nauvis
  position: [-45, 0]
  prototype: fisl-source-port
```

At READY, exactly one compatible entity must resolve.

Additional tag-based authoring sugar may be added if implemented reliably, but the resolved binding always identifies the exact endpoint used.

For conserved-ledger WIP, standard port bindings/apparatus must also satisfy ADR 0017's hardened one-way protocol requirements.

### 11.2 Material

```yaml
material:
  item: fisl-rough-workpiece
  quality: normal
```

Canonical v1 Factory Physics workpieces use normal quality.

### 11.3 Source supply

Replenish:

```yaml
supply:
  mode: replenish
  target: 400
  active_phases:
    - warmup
    - measured
```

Scheduled:

```yaml
supply:
  mode: scheduled
  active_phases:
    - measured
  schedule:
    type: constant
    rate: 180/min
  external_buffer:
    capacity: 2000
```

Inactive phases create no new scheduled supply/replenishment action, but existing staging/external inventory remains governed by the port contract.

### 11.4 Sink demand

```yaml
demand:
  id: customer_demand
  shortage_policy: backlog
  allocation: fifo
  active_phases:
    - measured
  schedule:
    type: constant
    rate: 60/min
```

V1 demand shortage policy is `backlog`; allocation is `fifo`.

A sink without `demand` remains a pure output boundary.

## 12. `flows`

A flow is the compatibility anchor for WIP, throughput, and cycle time.

```yaml
flows:
  workpiece_flow:
    system: factory
    unit: workpiece
    basis:
      type: conserved_work_unit
      materials:
        fisl-rough-workpiece: 1
        fisl-machined-workpiece: 1
        fisl-finished-workpiece: 1
    entry_ports:
      - workpiece_source
    completion_ports:
      - finished_goods
    loss_ports: []
```

Compiler validates:

- all ports belong to the same declared system;
- entry ports are sources;
- completion/loss ports are sinks;
- material mappings are exact/rational;
- canonical conserved-flow recipes satisfy declared conservation where compiler/runtime validation can establish it.

## 13. `metrics`

Metrics are keyed objects. References always use metric IDs.

V1 implementation SHOULD use a discriminated union on `type`.

### 13.1 `wip`

Canonical conserved-flow total WIP:

```yaml
line_wip:
  type: wip
  flow: workpiece_flow
  method: conservation_ledger
  validation:
    physical_census:
      required: true
      every: 60t
      discrepancy_tolerance: 0
```

Under ADR 0017, the ledger produces exact total point WIP each tick from initial WIP plus boundary/loss transactions. The coarse physical census independently validates/decomposes that ledger and is not silently reconciled into it.

A different future WIP method requires its own explicit semantics rather than inheriting this profile accidentally.

### 13.2 `material_inventory`

```yaml
raw_inventory:
  type: material_inventory
  system: factory
  materials:
    - iron-plate
    - copper-plate
```

Does not imply scalar WIP.

### 13.3 `current_value`

```yaml
current_wip:
  type: current_value
  source: line_wip
```

Used primarily for live disclosure of a current point-state metric.

### 13.4 `aggregate`

```yaml
average_wip:
  type: aggregate
  source: line_wip
  aggregation: time_mean
  window:
    phase: measured
```

Supported v1 aggregation operations:

```text
time_integral
time_mean
min
max
percentile
sum/count where source semantics permit
```

Percentile requires explicit weighting + quantile method.

### 13.5 `throughput`, `input_rate`, `output_rate`

```yaml
measured_throughput:
  type: throughput
  flow: workpiece_flow
  window:
    phase: measured
```

Rate windows may be fixed phase/interval or trailing windows.

### 13.6 `production_state`

```yaml
machine_state:
  type: production_state
  entities: line_machines
  adapter: crafting_machine
  classification_profile: factory_physics_v1
```

Produces per-entity raw/classified state data.

### 13.7 `state_fraction`

```yaml
line_starved_fraction:
  type: state_fraction
  source: machine_state
  entities: line_machines
  state: starved
  entity_aggregation: pooled_machine_time
  denominator: full_window
  window:
    phase: measured
```

Denominator may instead name an explicit eligible state set.

### 13.8 `on_time_item_rate`

```yaml
customer_service:
  type: on_time_item_rate
  demand: customer_demand
  cohort_window:
    phase: measured
  max_wait: 30s
  observation_horizon:
    through_phase: service_tail
```

The compiler validates the direct property:

```text
observation_horizon_end >= latest_selected_cohort_deadline
```

rather than requiring an arbitrary extra tail interval.

### 13.9 `demand_wait_percentile`

Requires explicit quantity weighting and deterministic quantile method.

### 13.10 `cycle_time`

Continuous flow:

```yaml
loaded_cycle_time:
  type: cycle_time
  flow: workpiece_flow
  method: little_law_derived
  wip_metric: average_wip
  throughput_metric: measured_throughput
```

Probe/cohort method variants use fields required by ADR 0009.

### Phase window

```yaml
  phase: measured
```

### Explicit authoring interval

```yaml
window:
  start: 5m

```

### Trailing

```yaml

  trailing: 60s
  startup: not_available_until_full
```

```json
{"start_tick":18000,"end_tick":90000}
```

## 16. `visibility`

```yaml
visibility:
  learner_live:
    metrics: [current_wip, live_throughput]
    objectives: [service_requirement]

  learner_post_run:
    metrics: [average_wip, measured_throughput]
    objectives: [service_requirement, minimize_wip]

    metrics: all_declared
    diagnostics: [coverage, protocol_violations, balance_errors]
```

Visibility IDs must reference declared metrics/objectives/diagnostic categories.

Visibility participates in resolved experiment identity.

## 17. `learning`

`learning` is explanatory/course metadata rather than runtime scientific logic.

Recommended fields:

```text
concepts
represents_directly
modifies
remains_absent
warranted_conclusions
not_warranted
instructor_notes
```

These fields belong to the scenario package/source identity but are excluded from the `ResolvedScenario` hash unless a future field is explicitly declared behavior-affecting.

## 18. Cross-reference and semantic validation

The compiler MUST fail before launching Factorio when any of these occur:

- duplicate IDs;
- missing references;
- invalid phase/window reference;
- nonpositive duration;
- duration not representable as whole ticks;
- source used as completion sink or sink used as entry source;
- ports in a flow belong to incompatible systems;
- WIP scalar lacks a defensible flow-unit basis;
- `conservation_ledger` WIP is requested for a flow that cannot satisfy ADR 0017 conservation requirements;
- Little's-Law cycle time references incompatible flow/window metrics;
- percentile lacks an explicit supported weighting/method;
- state fraction uses a bare/undefined utilization denominator;
- service metric observation horizon cannot resolve selected cohort deadlines under strict canonical configuration;
- objective references an incompatible/undefined metric;
- learner visibility references undeclared objects;
- port bindings are structurally incomplete;
- unsupported v1 policies are requested;
- unknown fields appear where strict schema validation applies.

Runtime READY validation then resolves/validates world-dependent facts such as actual entity bindings, hardened port apparatus, initial WIP census, and supported prototypes.

## 19. Compiler-generated observation plan

Scenario authors do not manually enumerate every primitive observation.

The Python compiler derives an observation plan from metrics/objectives/visibility dependencies.

Example dependency closure:

```text
loaded_cycle_time
  -> average_wip
      -> line_wip (conservation_ledger)
          -> initial WIP census
          -> source admissions
          -> completion/loss transactions
          -> periodic physical census validation
  -> measured_throughput
      -> finished_goods sink_delivery

customer_service
  -> customer_demand cohorts
  -> demand_created / cohort allocation / demand_fulfilled
```

The `ResolvedScenario` includes the resulting observation plan or a normalized equivalent so:

- Lua knows what to instrument;
- provenance records what was expected;
- missing coverage can be detected;
- Python can independently recompute results.

## 20. Resolved and run-specific runtime configuration

### 20.1 `ResolvedScenario` requirements

The stable canonical resolved document contains at least:

```text
spec/schema/compiler semantic versions
resolved phase tick boundaries
time/pause/game-speed policy
zone/system definitions
entity-set selectors
port bindings + normalized policies + rational schedules
flow definitions
runtime-required metric/observation definitions
objective definitions needed for in-game evaluation
visibility definitions needed for in-game UI
observation plan
```

It contains no run ID or actual run seed.

The compiler canonicalizes this object and computes:

```text
resolved_scenario_hash
```

### 20.2 `RunConfiguration` requirements

Before launch/configuration, the controller creates:

```text
run_id
resolved_scenario_hash
actual experiment_seed
protocol/config-envelope version
execution mode: interactive | headless
```

For the canonical interactive POC, the run profile additionally resolves operational settings equivalent to:

```text
server_auto_pause: false
disconnect_policy: abort
```

according to ADR 0018. These settings must participate in provenance/fingerprint identity when they can alter the learner's experimental condition.

The runtime may receive a wrapper containing both the `ResolvedScenario` and `RunConfiguration`, but the wrapper itself is **not** the stable resolved-scenario hash input.

### 20.3 Reproducibility identity

The run manifest/fingerprint combines the stable resolved scenario identity with actual run inputs/environment according to ADR 0013:

```text
resolved_scenario_hash
+ actual seed
+ baseline hash
+ Factorio/FISL/mod identities
+ behavior-affecting run profile
-> reproducibility fingerprint
```

`run_id` is deliberately excluded from the fingerprint.

Explanatory prose may be omitted from runtime configuration while remaining in the run package/report.

## 21. Python implementation direction

The Python implementation SHOULD provide:

```text
AuthorScenario models
ResolvedScenario models
RunConfiguration models
cross-reference/dimensional validators
compiler
canonical ResolvedScenario serializer/hasher
reproducibility-fingerprint builder
JSON Schema export
human-readable validation errors
```

Pydantic 2.x is the preferred model/validation layer. YAML is an authoring serialization only; the compiler should convert YAML to typed Python models immediately.

The exact YAML parser is not scientific semantics and may be selected for robust YAML support/error locations.

---

## 22. Lua implementation direction

Lua receives only resolved plain data plus the per-run configuration envelope.

Runtime validation focuses on:

- protocol/spec compatibility;
- `ResolvedScenario` content hash/transfer integrity;
- run-config/hash linkage;
- actual world bindings;
- prototype/entity compatibility;
- runtime measurement adapter support;
- clean baseline/run state;
- interactive/headless connection-policy consistency.

Lua SHOULD NOT reproduce Python's authoring/schema compiler.

---

## 23. Definition of done for schema implementation

The v1 schema implementation is ready when:

1. the complete teaching example parses and compiles;
2. resolved phase/window/rate arithmetic is exact;
3. every cross-reference is validated before launch;
4. incompatible WIP/throughput/cycle-time definitions fail compilation;
5. service deadlines/horizons validate using the actual latest-deadline property;
6. objective/visibility references validate;
7. canonical `ResolvedScenario` JSON + stable hash are produced without `run_id` or actual seed;
8. a separate `RunConfiguration` contains `run_id`, actual seed and resolved-hash reference;
9. retries with identical resolved semantics can have different run IDs while retaining the same resolved hash;
10. reproducibility fingerprint changes with behavior-affecting run inputs such as seed/environment but not run ID;
11. canonical interactive POC configuration resolves `pause_policy: prohibited`, auto-pause disabled, and disconnect-abort behavior;
12. JSON Schema/documentation can be generated from the typed models;
13. Lua can accept the resolved/run envelope without YAML parsing or semantic guessing;
14. the compiler can derive the observation-plan dependency closure required by Labs 0–6.
